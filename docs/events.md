# Initial RabbitMQ Event Contract

This document defines the smallest RabbitMQ contract required for the first-stage order-to-shipment flow. Events are integration messages, not shared domain models. Publishers own their event meaning; consumers store only the data required by their own responsibilities.

## Broker conventions

| Item | Initial contract |
| --- | --- |
| Exchange | `platform.events` |
| Exchange type | Topic |
| Routing key | Lowercase dotted form of the event name, for example `commerce.order.created` |
| Event type | PascalCase name in the envelope, for example `OrderCreated` |
| Versioning | Integer `event_version`, starting at `1`; incompatible changes require a new version or event type. |
| Delivery | At-least-once; consumers must tolerate duplicate deliveries. |
| Ordering | No global ordering guarantee. A consumer may rely only on the causal relationship represented by the event chain. |

The exchange and routing-key names are part of this first-stage contract. Queue names and deployment topology may be chosen by the implementation as long as each service receives the events listed below and applies the retry and dead-letter rules.

## Common event envelope

Every event uses the following envelope:

```json
{
  "event_id": "uuid",
  "event_type": "OrderCreated",
  "event_version": 1,
  "occurred_at": "2026-01-01T12:00:00Z",
  "correlation_id": "uuid",
  "causation_id": null,
  "payload": {}
}
```

### Envelope rules

- `event_id` uniquely identifies one published event and is the primary deduplication key.
- `event_type` must match the documented event name.
- `event_version` is an integer and is required even when the value is `1`.
- `occurred_at` is an ISO 8601 UTC timestamp generated by the publisher.
- `correlation_id` identifies the end-to-end lifecycle. The first publisher creates it; derived events preserve it.
- `causation_id` identifies the immediately preceding event. It is `null` for the first event and otherwise contains the parent `event_id`.
- `payload` contains only the event-specific fields documented below.

If a message enters the flow without a correlation ID, its publisher creates a UUID before publishing. Consumers must never replace an existing correlation ID.

## Event catalog

All payloads below are the minimum version-1 contract. Additional fields require a compatibility review; consumers must ignore unknown fields so additive changes remain possible.

| Event | Publisher | Consumer | Routing key |
| --- | --- | --- | --- |
| `OrderCreated` | `commerce-laravel` | Commerce-owned payment simulator | `commerce.order.created` |
| `PaymentApproved` | `commerce-laravel` | Commerce-owned shipment-request handler | `commerce.payment.approved` |
| `ShipmentRequested` | `commerce-laravel` | `logistics-go` | `commerce.shipment.requested` |
| `ShipmentCreated` | `logistics-go` | `notifications-nestjs` | `logistics.shipment.created` |
| `NotificationRequested` | `notifications-nestjs` | Notification delivery handler in `notifications-nestjs` | `notifications.requested` |

### `OrderCreated` — version 1

```json
{
  "order_id": "order-uuid"
}
```

Published after `commerce-laravel` has durably created the order in its own database. The first-stage payment simulation is the only consumer required for this contract.

### `PaymentApproved` — version 1

```json
{
  "order_id": "order-uuid",
  "payment_status": "approved",
  "simulated": true
}
```

This is a commerce-owned simulated transition. It is not evidence of an external authorization and does not introduce a payment service.

### `ShipmentRequested` — version 1

```json
{
  "order_id": "order-uuid"
}
```

Published only for an approved order. Shipment address, carrier, rate, package dimensions, and delivery estimates are not part of the initial contract.

### `ShipmentCreated` — version 1

```json
{
  "order_id": "order-uuid",
  "shipment_id": "shipment-uuid",
  "shipment_status": "created"
}
```

Published after `logistics-go` has durably created its shipment record. It does not represent carrier booking or delivery completion.

### `NotificationRequested` — version 1

```json
{
  "order_id": "order-uuid",
  "shipment_id": "shipment-uuid",
  "notification_type": "shipment_created"
}
```

Published by `notifications-nestjs` after consuming `ShipmentCreated`. Its delivery handler records the request and simulates delivery; recipient resolution and external notification providers are outside this contract.

## Correlation and causation example

All events for one order share `correlation_id`:

```text
OrderCreated
  event_id = A, causation_id = null, correlation_id = C
PaymentApproved
  event_id = B, causation_id = A,    correlation_id = C
ShipmentRequested
  event_id = D, causation_id = B,    correlation_id = C
ShipmentCreated
  event_id = E, causation_id = D,    correlation_id = C
NotificationRequested
  event_id = F, causation_id = E,    correlation_id = C
```

The identifiers are illustrative. A consumer must preserve `correlation_id` and set the new event's `causation_id` to the event that caused its state transition.

## Idempotency expectations

RabbitMQ delivery is at-least-once. Every consumer must:

1. Detect whether the incoming `event_id` has already been successfully processed.
2. Skip duplicate business work and acknowledge a known-successful duplicate.
3. Record the event as processed in the same local durability boundary as the business change, or use an equivalent mechanism that prevents a crash window from applying the change twice.
4. Avoid deduplicating by `order_id` alone: one order can legitimately produce different event types and versions.

The initial design does not prescribe a shared idempotency library or cross-service store. Deduplication state belongs to the consuming service.

## Retry and dead-letter behavior

- A consumer acknowledges a message only after its local database work succeeds.
- A transient failure is retried up to three delivery attempts after the initial attempt, for a maximum of four attempts total.
- Retry delays are implementation-configurable, but must be increasing whole milliseconds and must not busy-loop. The retry count must be carried in broker headers or an equivalent transport-level mechanism. The current logistics and notifications workers use three stages: 1s, 5s, and 15s.
- A permanent validation, unsupported-version, or business-rule failure is not retried. It is routed directly to the consumer's dead-letter queue.
- After the final transient retry fails, the message is routed to the consumer-specific dead-letter queue through the dead-letter exchange `platform.events.dlx`.
- Dead-lettered messages retain the original event envelope, identity properties, and bounded service-scoped metadata needed to diagnose the failure, including the classification and retry count. Consumers must not copy arbitrary incoming headers, credentials, or payload data into retry metadata or logs.
- Dead-letter queues are for inspection and controlled replay. Replay must preserve the original `event_id` and correlation data and must occur only after the cause is understood.

The logistics and notifications consumers declare additive durable TTL retry queues. A transient failure is published to the next service-owned retry queue and the publication is confirmed before the original delivery is acknowledged. The retry queue dead-letters back to the original event routing key; after the third delayed retry, or for a permanent failure, the consumer publishes to its final DLQ. A malformed notification message is sent through broker `reject(message, false)` because its envelope cannot be safely reconstructed. A publication or ACK failure must leave the original delivery unacknowledged or requeued so redelivery remains possible; a confirmed retry followed by an ACK failure can therefore produce a duplicate, which inbox idempotency must absorb.

The contract does not define automatic replay, message loss, or silent discard. A dead-lettered message remains available for operator or development-time inspection.

## Happy-path flow

```text
OrderCreated
  commerce-laravel
      -> PaymentApproved (simulated)
  commerce-laravel
      -> ShipmentRequested
  logistics-go
      -> ShipmentCreated
  notifications-nestjs
      -> NotificationRequested
  notifications-nestjs
      -> simulated notification handling
```

The payment approval and notification delivery are simulated. Carrier integration, real payment authorization, recipient/channel resolution, delivery tracking beyond the shipment record, and failure compensation are outside the first-stage contract.
